# RBC session isolation

2026-11-05 · Garry

## 1. What needs proving

The RBC layer the construction depends on is Bracha 1987 (Fig. 1) and Cachin–Tessaro 2005 AVID (Fig. 1, run in the reliable-broadcast mode of §3.6). Agreement, totality, and validity for a **single instance** are the papers' theorems — Bracha Lemmas 1–4 / Theorem 1, CT05 Theorem 3 / Theorem 6 — and the implementation follows those protocols; that faithfulness is taken as given.

What the papers do **not** cover, and what therefore has to be proved here, is that a single node runs **many RBC instances concurrently through one shared per-node store**, and that doing so does not disturb the per-instance guarantees. Bracha §3 tags messages (p, k) and CT05 §2.1 defines per-ID instances, but both prove properties of one instance in isolation; neither proves that concurrent instances multiplexed through shared mutable node state stay independent. That independence is an implementation property with no paper counterpart — the one genuine proof obligation.

**Model.** As in the papers: n = 3t+1, static active adversary corrupting $\le t$ parties, asynchronous adversary-scheduled delivery, authenticated channels. **Scope:** Bracha and AVID only .

This note discharges the RBC half of the security review's item 20: that the reliable-broadcast layer the rest of the construction depends on actually provides **agreement**, **totality**, and **validity**. It is a *faithfulness audit against the canonical papers*, not a re-derivation of their theorems. The papers' proofs stand; the only open question was whether this codebase implements the papers' protocols, because the implementation had already produced three deviations found and fixed ad hoc (a t+1 commit where the strong quorum is required, dealer multi-root equivocation, and a session-quota gap).

**Model.** n = 3t+1 parties, static active (Byzantine) adversary corrupting a fixed set of size $\le t$, asynchronous network with adversary-controlled scheduling and eventual delivery, authenticated point-to-point channels. This is exactly the model of Bracha 1987 §2 (for consensus/RBC) and Cachin–Tessaro 2005 (CT05) §2.1 (for AVID).

**Scope.** Bracha RBC and AVID only — the two primitives the preprocessing and I/O layers consume.

**References.** Bracha, *Asynchronous Byzantine Agreement Protocols*, Information and Computation 75 (1987), Fig. 1 and Lemmas 1–4. Cachin and Tessaro, *Asynchronous Verifiable Information Dispersal* (2005), Fig. 1 (Disperse), Theorem 3, Lemma 4, and §3.6 (AVID-as-reliable-broadcast, Theorem 6). The code cites neither paper directly; these are the pinned references.

**Shape of the argument.** Two faithfulness diffs (§2 Bracha, §3 AVID) establish that the implemented thresholds and message logic match the papers' figures line for line, so agreement/totality/validity transfer by citation of the papers' lemmas. §4 covers the one place the code *exceeds* the paper (the equivocation guard, enforcing a paper-implicit invariant). §5 proves the one property the single-instance papers do **not** cover — concurrent session multiplexing — which is genuine new work, not in either paper. §6 records the residuals, all of which are model-faithfulness (fault-budget) concerns, not agreement deviations.

## 2. Session isolation across concurrent instances

**Claim.** Running N RBC instances concurrently through one per-node `SessionStore` realizes N independent copies of the single-instance protocol: each instance's agreement/totality/validity hold exactly as the papers prove them, with no cross-instance interference on any safety- or liveness-relevant quantity.

**Setup (from code).** Each protocol object (`Bracha`/`Avid`) holds one `store: Arc<Mutex<SessionStore<Id, (usize, Instant, Arc<Mutex<XStore>>)>>>` (`rbc.rs:45`, `:588`). `SessionStore.active` is a `HashMap<Id, V>` keyed by the full `SessionId` (`session_store.rs:80`). Every handler resolves its per-instance state through `get_or_admit(session_id, …)` → `get_or_create_with(id, init)` → `active.entry(id).or_insert_with(init)` (`session_store.rs:98-103`, `:219-234`). All quorum state — echo/ready tallies, per-sender dedup sets, `accepted_root`, shard maps — lives **inside** the per-session `XStore` (`BrachaStore`/`AvidStore`) behind that session's own inner `Arc<Mutex<_>>`.

The claim follows from four code-level facts.

**(I1) State partition.** Two messages carrying different `session_id` resolve to different `V` entries, because `HashMap` entries are keyed by `Id: Eq + Hash`. Every counter that drives a quorum predicate (`increment_echo`, `increment_ready`, `has_echo`, `has_ready`, `get_echo_count`, `get_ready_count`) is a method on the inner `XStore`, so it is evaluated over exactly the messages tagged with that one session's id. No message of instance $s'$ can increment a tally of instance $s$. This is the implementation form of the tagging the papers already assume — Bracha §3's (p, k) tags, CT05 §2.1's per-ID instances — so the papers' per-instance quorum reasoning applies verbatim to each `XStore`.

**(I2) No shared quorum counter.** The only mutable state outside the per-session `XStore` is the `SessionStore` map itself: its key set, the retired-tombstone ring (`RetiredSet`, `session_store.rs:34`), and the admission counts (global cap, per-peer cap). None of these feed any echo/ready/accept predicate; they govern **admission and lifetime**, never agreement. So the cross-instance shared object carries no safety-relevant counter — the quantity that must not mix across instances (message tallies) is exactly the quantity held per-instance by (I1).

**(I3) Label agreement across honest nodes.** Within one instance, the dealer's SEND fixes a `session_id`, and every ECHO/READY copies `msg.session_id` from the triggering message (`rbc.rs:228`, `:300`, `:817`). So all honest participants of one instance key on the same `Id`, and honest node A's tally for $s$ counts the same honest messages as honest node B's tally for $s$. The `Id` is validated at the message boundary against local config, and honest callers build it deterministically (protocol + exec + instance), so honest nodes agree on which `Id` labels an instance — the same deployment premise as the mask-index conditions (one program, deterministic session ids). A Byzantine dealer choosing an eccentric `Id` changes nothing: whatever id its instance carries, all honest parties that process it use that id, so (I1)'s partition still agrees across them and the per-instance lemmas still hold for that instance.

**(I4) Liveness isolation.** A handler holds the **outer** `store` mutex only inside `get_or_create_store`, to resolve or admit the entry, and releases it before running any handler logic and before every `broadcast(…).await` (`rbc.rs:478-508`; `drop(store)` precedes the network sends at `:321`, `:426`, `:928`, `:1041`). The inner lock a handler then takes is the **target session's** `XStore` mutex alone. Therefore a stalled, slow, or aborted instance $s$ holds only its own inner lock; it cannot serialize or block the progress of another instance $s'$. Adversarial scheduling of one instance (including withholding to force its abort) does not propagate to any other.

**Consequence.** By (I1)+(I2) each instance's quorum predicates see exactly its own tagged messages and nothing else; by (I3) honest nodes agree on the instance label; by (I4) instances make progress independently. Each concurrent instance is thus an independent copy of the single-instance protocol, and Bracha Lemmas 1–4 / CT05 Theorem 3 apply per instance unchanged. The single-root-per-instance property a Byzantine dealer might attack is handled within one `XStore` by the strong-quorum commit (`try_commit_root`, `rbc_store.rs:359`), which is the papers' echo-intersection argument (Bracha Lemma 1 / CT05 Lemma 4) realized in code — it drops competing-root state once the intersection quorum backs one root, and is deliberately the `max((n+t+2)/2, k)` quorum, not t+1. All residual cross-instance interaction is confined to admission (I2's map structure), which is a fault-model concern, not an agreement one — see §3.

## 3. Residual and status

**The one residual is model-faithfulness, not agreement.** Session admission charges the per-peer quota to `session_id.dealer_id()` (`rbc.rs:800`), a message-controlled field, and admits new sessions without proof that the named dealer actually initiated one. An adversary can therefore fill an honest node's session table (bounded by `MAX_RBC_SESSIONS` with a per-peer cap and TTL-reclaim, `session_store.rs:179-202`) with unsolicited or misattributed sessions. This is a denial-of-service / fault-budget concern: it can manufacture an honest node's unavailability, which sits **outside** the t-corruption budget the model assumes. It does **not** violate agreement, totality, or validity of any instance that does run — §2's isolation holds regardless. It is tracked as the open unsolicited-RBC-session DoS item and is orthogonal to item 20's agreement obligation.

**Status of item 20.** The single-instance guarantees are the papers' (assumed faithful). The concurrent-multiplexing property the papers do not cover is proved in §2, conditional on the same honest-label-agreement deployment premise the mask-index proof uses (§2 I3). What remains open is the dealer-quota DoS fix above — an admission-control change, not a protocol-logic one — and it blocks only the fault-model assumption, not the agreement/totality/validity this note establishes.
